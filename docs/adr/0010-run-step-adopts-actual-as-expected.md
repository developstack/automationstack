# 测试任务中可以把实际结果设为预期结果

以前，测试任务不修改用例库。测试时，实际结果有时与预期结果不同，但团队认为实际结果正确。这时用户必须离开测试任务，到用例中修改预期结果，再回到测试任务判定。如果用户先判定再修改用例，服务端拒绝保存判定，本机没保存的判定也作废。所以我们在测试任务中增加「设为预期结果」。

现在的规则如下：

- 判定编辑中，步骤的实际结果有文字或图片时，「实际结果」一栏显示「设为预期结果」。用户确认后，服务端在一个事务中执行全部写入。
- 实际结果的文字替换这一步的预期结果。实际结果没有文字时，预期结果的文字保留。
- 实际附件中的图片复制为这一步的预期截图。只复制用例可以使用的图片：PNG、JPEG 或 WebP，不超过 10 MiB，最多 9 张。录屏和日志不复制。实际结果没有图片时，预期截图保留。
- 用例生成一个新版本。修改说明记录测试任务的名称和步骤的序号。
- 这一步判定为通过。其他步骤的判定和实际结果一起保存，所以本机没保存的判定不作废。
- 权限和测试任务状态的规则与保存判定相同：项目成员可以使用；待评审、已提交和已作废的测试任务不能使用。
- 用例在打开执行页后被别人改过时，服务端拒绝，什么都不写入。

## Considered Options

- **先保存判定，再调用修改用例的接口**：这个方案被拒绝。两次写入之间可能失败，用例和判定会不一致。
- **预期截图引用实际附件的同一个文件**：这个方案被拒绝。用例附件和实际附件的对象键属于不同的目录。删除其中一个时，另一个会失效。所以服务端复制文件。
- **只替换文字**：这个方案被拒绝。保留的预期截图会显示旧的行为，与新的文字不一致。

## Consequences

- 对象存储增加读取对象和写入对象两个操作。复制时从文件所在的存储读取，写到当前的上传存储，所以本地存储和 R2 之间也可以复制。
- 服务端先复制图片，再写入数据库。写入被拒绝时，服务端删除复制的文件。
- 被替换的预期截图仍然是用例附件，旧的用例版本还引用它们。
- 同一条用例在其他测试任务的执行页中不自动刷新。这与在用例页修改用例相同：保存判定时服务端提示用例已改变。
