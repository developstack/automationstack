## 摘要

本报告从读者和读者的问题推出项目概览的指标，不从现有数据推出指标。

#26 的概览（提交 56e98a0）只显示当前快照。它没有时间窗口、趋势和测试任务的数据。「高优先级陈旧用例」区域使用 `test_cases.updated_at`。调整用例顺序也会改变这个字段，所以这个区域的数据不可靠。

本报告推荐 10 个指标。第一屏放 4 个指标：用例状态组成、新增用例、进行中的测试任务、执行覆盖率。

推荐的 10 个指标都能用只读查询从现有数据表算出。#53 需要新增 6 个只读查询，并在现有的 `projectStats.overview` 查询中增加 2 个字段。需要新数据（新表或新字段）的指标都列在「不推荐的指标」中，不进入第一版。

现有概览的区域结论如下：删除方格矩阵、「高优先级陈旧用例」和「最近改动」列表；修改用例状态卡片和优先级分布；保留每个区域独立加载、空状态和重试。

## 1. 术语

本报告使用 `CONTEXT.md` 中的术语：用例、用例状态（草稿、生效、废弃）、测试任务、测试任务状态（待评审、待测试、测试中、已完成、已提交）、执行结果（未测、通过、失败、阻塞、跳过）、项目 owner、项目成员。

本报告另外定义下面的术语。每个术语在全文中只有一个意义。

| 术语 | 定义 |
|---|---|
| 有结论 | 执行结果不是未测。测试任务的完成进度使用这个定义，与 `computeCompletionRate` 一致。 |
| 已执行 | 执行结果是通过或失败。阻塞和跳过表示用例没有真正执行。执行覆盖率使用这个定义，与 `computePassRate` 的分母一致。 |
| 执行覆盖率 | 在一个时间窗口内已执行的生效用例条数，除以生效用例总数。 |
| 时间窗口 | 一个指标统计的时间范围，例如「过去 7 天」。「过去 7 天」指从现在向前 7×24 小时。 |
| 7 天区间 | 趋势图的一个数据点。从现在向前切成 12 个连续的 7 天区间，最后一个区间就是「过去 7 天」。 |
| 进行中的测试任务 | 测试任务状态是待评审、待测试、测试中或已完成的测试任务，即还没有提交的测试任务。 |
| 第一层模块 | 模块树中没有父模块的模块。 |
| 条形码式进度条 | #26 用例状态卡片中的竖线条（`status-barcode.tsx`）。一条竖线表示一条或多条用例。它是唯一的进度条样式。 |
| 大数字 | 一个大字号的数字，带一行小字说明。 |

## 3. 图形选择规则

维护者在 #52 的两条评论中给出图形规则。后一条评论修改前一条评论。本报告按下面的规则选择图形：

1. **条形码式进度条**：表示一组用例中各部分的数量，并且这个图形出现在列表的一行中，或多个实例并排。例如每个测试任务的完成进度、每个优先级的占比。竖线让读者看到用例的数量，不只是百分比。
2. **圆环图（`PieChart`，设置 `innerRadius`）**：表示一个整体的组成，类别最多 5 个，每个类别有固定的状态色。例如用例状态、执行结果。中心显示总数。
3. **环形进度图（`RadialBarChart`）**：表示整个项目的一个比率，这个比率在页面上只出现一次。例如执行覆盖率。
4. **柱状图、条形图（`BarChart`）**：比较类别之间的数量，或比较各 7 天区间内的离散计数。
5. **折线图、面积图（`LineChart`、`AreaChart`）**：表示随时间变化的趋势。
6. **大数字**：表示读者需要直接读出的一个数。
7. **列表**：读者需要点进去处理的对象，例如停滞的测试任务、有缺口的模块。

除条形码式进度条外，图表都使用 `packages/ui/src/components/chart.tsx` 中的 shadcn Chart 组件：`ChartContainer`、`ChartTooltip`、`ChartTooltipContent`、`ChartLegend`、`ChartLegendContent`。仓库中的 Recharts 版本是 3.10.1。

规则 1 和规则 3 的边界见第 10 节的开放问题 1。

### 3.1 现有图表组件做不到的图形

| 图形 | 原因 |
|---|---|
| 条形码式进度条 | Recharts 没有「一条竖线表示 N 条用例」的图形。用 `BarChart` 画几百个细柱可以模拟，但每个细柱都是一个 SVG 元素和一个事件处理对象，开销大，并且无法使用现有的状态色类名。维护者决定保留现有的手写组件，并把它做成可复用组件（#53）。 |
| 大数字 | 它是文字，不是图表。 |
| 列表 | 它是文字和链接，不是图表。 |

## 4. 指标清单

每个指标一节，格式相同。「数据来源」中的表名和字段名来自 `packages/db/src/schema/`。

### M1 用例状态组成（P1）

- **回答的问题**：Q1。用例库有多少条用例？其中多少条能用来测试？
- **决定**：草稿占比高，或草稿停留时间长时，项目 owner 安排评审。
- **定义和公式**：
  - 用例总数 = 项目中 `test_cases` 的行数。
  - 生效、草稿、废弃的条数 = 按 `status` 计数。
  - 停留超过 14 天的草稿 = `status = 'draft'` 并且 `created_at` 早于现在减 14 天的条数。
  - 时间窗口：无，显示当前状态。
- **数据来源**：`test_cases.status`、`test_cases.created_at`。
- **可行性**：用例总数和三种用例状态的条数现成，来自 `projectStats.overview`。停留超过 14 天的草稿需要在 `projectStats.overview` 中增加 1 个计数字段 `staleDraftCount`。
- **推荐图形**：圆环图。`PieChart` + `Pie`（`innerRadius`），中心用 `Label` 显示用例总数。图例列出三种用例状态的条数和百分比。图例下方一行小字：「其中 N 条草稿超过 14 天」。
- **图形理由**：用例状态是一个整体的组成，只有 3 个类别，每个类别有固定的状态色。这符合规则 2。维护者的第二条评论把用例状态列为圆环图的例子。`overview-donut-chart.tsx` 已经实现带中心文字的圆环图，测试任务报告的执行结果卡片在使用它。#53 可以复用这个组件。
- **为什么比替代指标好**：只显示用例总数时，读者不知道多少条能用来测试。用例总数也容易变大，例如复制用例。显示组成后，读者能直接看到生效用例的比例。

### M2 新增用例（P1）

- **回答的问题**：Q2。过去 7 天新增多少条用例？用例库在增长还是停滞？
- **决定**：新增数连续几个 7 天区间都很低时，项目 owner 检查编写用例的工作安排。新增数突然很高时，项目 owner 检查是否有批量导入。
- **定义和公式**：
  - 过去 7 天新增 = `created_at` 在过去 7 天内的用例条数。包含所有用例状态。
  - 对比值 = 前一个 7 天区间的新增条数。显示差值，例如「比前 7 天多 12 条」。
  - 过去 7 天修改 = 过去 7 天内有新版本、并且版本号大于 1 的用例条数（去重）。这个数代替「最近改动」列表，见第 6 节。
  - 趋势 = 12 个 7 天区间，每个区间的新增条数。
- **数据来源**：`test_cases.created_at`；`case_versions.case_id`、`case_versions.version`、`case_versions.created_at`。
- **可行性**：需要新增只读查询 `projectStats.caseTrend`。查询用 `generate_series` 生成 12 个 7 天区间，再按 `created_at` 计数。数据有两个限制：
  - 被删除的用例不在 `test_cases` 中，所以历史区间只统计没有删除的用例。被测试任务引用的用例不能删除（`removeTestCaseInTx`），所以影响小。
  - 导入的用例和手工新建的用例都写入「创建用例」版本说明，查询不能可靠地区分。见第 10 节的开放问题 5。
- **推荐图形**：大数字显示过去 7 天新增，下面一行显示对比值和过去 7 天修改。右侧或下方是面积图：`AreaChart` + 一个 `Area`，X 轴是区间的开始日期，`ChartTooltipContent` 显示区间和条数。
- **图形理由**：维护者把「每周新增用例」列为折线图、面积图的例子。面积图的填充区域表示每个区间的数量，比单条线更容易看出多和少。最后一个数据点等于大数字，两者使用同一个时间窗口，读者不会看到两个不同的数。
- **为什么比替代指标好**：
  - 自然周（周一到周日）的当前周只有几天，最后一个数据点总是偏低。7 天区间没有这个问题，也不需要选择时区。
  - 「用例总数趋势」主要表示过去的累积，看不出最近是否停滞。

### M3 进行中的测试任务（P1）

- **回答的问题**：Q3。进行中的测试任务完成了多少？哪个停滞了？
- **决定**：安排测试工作的项目成员跟进停滞的测试任务，或重新分配执行人。项目 owner 提交已完成的测试任务。
- **定义和公式**：
  - 范围：进行中的测试任务，即 `submitted_at` 为空的测试任务。
  - 每个测试任务的完成进度 = 有结论的条数 / 用例条数。条形码式进度条按执行结果分段：通过、失败、阻塞、跳过、未测。
  - 距上次执行的天数 = 现在减去该测试任务中最大的 `executed_at`。没有执行结果时，用测试任务的 `created_at`。
  - 停滞：测试任务状态是待测试或测试中，并且距上次执行超过 7 天。
  - 排序：先显示停滞的测试任务，再按 `created_at` 从新到旧排序。最多显示 5 行，并显示「全部 N 个」的链接，链接到测试任务列表。
- **数据来源**：`test_runs.status`、`test_runs.created_at`、`test_runs.submitted_at`；`test_run_cases.result`、`test_run_cases.executed_at`。
- **可行性**：需要新增只读查询 `projectStats.activeRuns`。`listIngestRunSummaries`（`automation-ingest-repository.ts`）已经用同样的方法计算距上次执行的天数，`listTestRuns` 已经按执行结果计数。新查询可以合并这两个查询的计算。
- **推荐图形**：每个测试任务一行：名称、测试任务状态标签、条形码式进度条、「有结论 N / M」、距上次执行的天数。停滞的测试任务在天数旁边显示提示文字。
- **图形理由**：维护者把「测试任务的完成进度」列为条形码式进度条的例子。多个测试任务并排显示，符合规则 1。按执行结果分段后，读者在一行中同时看到进度和失败数。
- **为什么比替代指标好**：
  - 「进行中的测试任务数」只是一个数，读者不知道哪个测试任务需要处理。
  - 「所有测试任务的平均完成率」会把一个停滞的测试任务和几个快完成的测试任务混在一起。
  - 停滞使用「距上次执行的天数」，因为测试任务没有计划完成日期字段。

### M4 执行覆盖率（P1）

- **回答的问题**：Q4。过去 30 天，多少条生效用例真正执行过？没执行的在哪里？
- **决定**：安排测试工作的项目成员把没执行的生效用例放进下一个测试任务。P0/P1 用例的执行覆盖率低时，项目 owner 在发布前要求补充测试。
- **定义和公式**：
  - 分母 = 当前用例状态是生效的用例条数。
  - 分子 = 分母中，过去 30 天内在任一测试任务中已执行（通过或失败）的用例条数。
  - 第二个环：只统计 P0/P1 生效用例，时间窗口同样是 30 天。
  - 按第一层模块统计：每个第一层模块（包含子模块）中，过去 30 天没有执行的生效用例条数。显示最多 8 个模块，按条数从多到少排序。
  - 列表：过去 90 天没有执行的 P0/P1 生效用例，按上次执行时间从早到晚排序，最多 10 条。从来没有执行的用例排在最前面。
- **数据来源**：`test_cases.status`、`test_cases.priority`、`test_cases.module_id`；`test_run_cases.case_id`、`test_run_cases.result`、`test_run_cases.executed_at`；`test_runs.project_id`；`modules.parent_id`。
- **可行性**：需要新增只读查询 `projectStats.executionCoverage`。`test_run_cases` 有索引 `(case_id, executed_at desc)`，可以高效地取得每条用例的上次执行时间。第一层模块的汇总可以复用 `project-stats-coverage.ts` 中的递归 CTE。
- **推荐图形**：
  - 环形进度图：`RadialBarChart`，两个 `RadialBar`。外环是全部生效用例，内环是 P0/P1 生效用例。`PolarAngleAxis` 的 `domain` 设为 `[0, 100]`，并用 `background` 显示未完成的轨道。中心显示外环的百分比。
  - 横向条形图：`BarChart`（`layout="vertical"`），每个第一层模块一个条，长度是没有执行的生效用例条数。
  - 列表：过去 90 天没有执行的 P0/P1 生效用例，每条链接到用例管理。
- **图形理由**：执行覆盖率是整个项目的一个比率，在页面上只出现一次。这符合规则 3。两个环让读者直接比较全部用例和 P0/P1 用例。按模块的统计是类别之间的数量比较，这符合规则 4。列表给出可以直接处理的用例。
- **为什么比替代指标好**：
  - 它代替 #26 的「高优先级陈旧用例」。#26 用 `updated_at` 判断陈旧，但这个字段不表示内容的修改时间，见第 7 节。
  - 一条稳定的用例长期不修改是正常的。长期不执行才是风险。
  - 阻塞和跳过不算已执行，所以把用例标记为跳过不能提高执行覆盖率。

### M5 生效用例的最新执行结果（P2）

- **回答的问题**：Q5。现在有多少条生效用例处在失败或阻塞？
- **决定**：项目 owner 跟进失败用例关联的缺陷，并安排重新测试。测试任务列表的「重新测试」可以从失败用例新建测试任务。
- **定义和公式**：
  - 范围：生效用例中，过去 30 天内有结论的用例。
  - 每条用例取最新的执行结果，即 `executed_at` 最大的那一行的 `result`。
  - 类别：通过、失败、阻塞、跳过。过去 30 天没有结论的用例不在这个图中，它们已经显示在 M4 中。
  - 补充数字：最新执行结果是失败的 P0/P1 生效用例条数。
- **数据来源**：`test_run_cases.case_id`、`test_run_cases.result`、`test_run_cases.executed_at`；`test_cases.status`、`test_cases.priority`。
- **可行性**：需要新增只读查询 `projectStats.latestResults`。查询使用 `distinct on (case_id)` 并按 `executed_at desc` 排序。
- **推荐图形**：圆环图。`PieChart` + `Pie`（`innerRadius`），使用执行结果的状态色。中心显示失败和阻塞的条数之和。圆环下方一行：「其中 N 条 P0/P1 用例失败」。
- **图形理由**：执行结果组成是一个整体，最多 4 个类别，每个类别有固定的状态色。维护者把执行结果列为圆环图的例子。
- **为什么比替代指标好**：
  - 「项目通过率」把所有测试任务的执行混在一起。一条用例在多个测试任务中执行时，它被计算多次。
  - 取每条用例的最新执行结果，一条用例只计算一次，这和 Xray 按最新执行计算测试状态的方法一致。
  - 每个测试任务的通过率属于测试任务报告（#39），概览不重复显示。

### M6 每周执行结果（P2）

- **回答的问题**：Q6。测试工作量和失败数量在变多还是变少？
- **决定**：失败数量连续增加时，项目 owner 提出质量风险。执行数量下降时，项目 owner 检查测试任务的安排。
- **定义和公式**：
  - 每个 7 天区间：`executed_at` 在该区间内、并且有结论的 `test_run_cases` 行数，按执行结果分组。
  - 一条用例在一个测试任务中多次修改执行结果时，只计算最后一次，因为 `executed_at` 只保存最后一次的时间。
  - 12 个 7 天区间，与 M2 相同。
- **数据来源**：`test_run_cases.result`、`test_run_cases.executed_at`；`test_runs.project_id`。
- **可行性**：需要新增只读查询 `projectStats.executionTrend`。被删除的测试任务的执行结果也被删除（级联删除），所以历史区间只统计现存的测试任务。
- **推荐图形**：堆叠柱状图。`BarChart` + 4 个 `Bar`（通过、失败、阻塞、跳过），使用同一个 `stackId`。`ChartTooltipContent` 显示各执行结果的条数，`ChartLegend` 显示图例。
- **图形理由**：每个柱子是一个 7 天区间内的离散计数。柱子的高度表示工作量，分段表示执行结果。折线图只能显示比率或单个计数：显示通过率时，执行很少的区间也会显示 100%，读者会误解。
- **为什么比替代指标好**：
  - 「每周通过率」折线图隐藏了工作量。
  - `test_run_case_events` 保存每次修改执行结果的记录，但它也包含纠正错误的修改，会把一次执行计算两次。

### M7 测试任务新建和完成趋势（P2）

- **回答的问题**：Q7。测试任务完成的速度跟得上新建的速度吗？
- **决定**：新建的线持续高于完成的线时，项目 owner 减少新的测试任务，或增加执行人。
- **定义和公式**：
  - 新建：`test_runs.created_at` 在区间内的测试任务数。
  - 完成：测试任务状态是已完成或已提交，并且 `completed_at` 在区间内的测试任务数。
  - 12 个 7 天区间，与 M2 相同。
  - 大数字：过去 7 天完成的测试任务数。
- **数据来源**：`test_runs.created_at`、`test_runs.completed_at`、`test_runs.status`。
- **可行性**：需要新增只读查询 `projectStats.runTrend`。`completed_at` 的特点：测试任务从已完成回到测试中时，`buildStatusPatch` 把 `completed_at` 设为空；提交时不修改 `completed_at`。所以对已完成和已提交的测试任务，`completed_at` 是最后一次进入已完成的时间。
- **推荐图形**：折线图。`LineChart` + 两个 `Line`（新建、完成），`ChartLegend` 区分两条线。
- **图形理由**：维护者把「测试任务完成数」列为折线图的例子。两条线在同一个坐标中，读者直接比较两个速度。两个系列的柱状图需要并排的柱子，比较更难。
- **为什么比替代指标好**：
  - 「完成」使用 `completed_at`，不使用 `submitted_at`。自动提交在完成后 N 天发生（默认 3 天，`project_settings.auto_submit_after_completed_days`），所以 `submitted_at` 有延迟。
  - 「已完成的测试任务总数」只增不减，看不出最近的速度。

### M8 模块覆盖缺口（P2）

- **回答的问题**：Q8。哪些模块没有用例，或没有生效用例？
- **决定**：项目 owner 安排编写或评审该模块的用例。
- **定义和公式**：与现有查询相同。
  - 零用例：模块和子模块中没有用例。
  - 无生效用例：模块和子模块中有用例，但没有生效用例。
  - 只显示有缺口的模块。父模块和子模块都有缺口时，只显示父模块，避免重复。
- **数据来源**：`modules`、`test_cases.module_id`、`test_cases.status`。
- **可行性**：现成，来自 `projectStats.coverage`。只显示父模块的过滤在前端完成。
- **推荐图形**：标题旁的大数字显示有缺口的模块数。下面是列表：模块路径、缺口类型标签、用例条数，每行链接到用例管理中的该模块。没有缺口时显示「N 个模块都有生效用例」。
- **图形理由**：读者要处理的对象是模块，所以列表最直接。缺口的本质是「没有」，图表无法画出零长度的条。
- **为什么比替代指标好**：#26 的方格矩阵为每条用例画一个方格。读者的问题是「哪些模块没有用例」，答案是没有方格的行，读者必须在大量方格中找空行。详细评估见第 6 节。

### M9 生效用例的优先级分布（P3）

- **回答的问题**：Q9。优先级的分配合理吗？
- **决定**：P0/P1 占比过高时，项目 owner 重新评审优先级。优先级失去区分作用时，测试任务无法按优先级选择用例。
- **定义和公式**：生效用例按 `priority` 计数，再除以生效用例总数。草稿和废弃的优先级不影响测试，所以不统计。
- **数据来源**：`test_cases.priority`、`test_cases.status`。
- **可行性**：需要在 `projectStats.overview` 中增加一组按生效统计的优先级计数（`activePriorityCounts`）。现有的 `priorityCounts` 统计全部用例状态。
- **推荐图形**：每个优先级一行：等宽字体的 `P0`–`P3` 标签、条形码式进度条、「N 条 · M%」。竖线使用前景色，不使用颜色，因为 #19 规定优先级不用颜色。
- **图形理由**：维护者把优先级分布列为条形码式进度条的例子。4 行并排，符合规则 1。#26 的实心横条改为条形码式进度条，因为维护者决定不使用实心进度条。
- **为什么比替代指标好**：统计全部用例状态时，大量废弃用例会改变占比，但它们不进入测试任务。

### M10 自动化执行占比（P3）

- **回答的问题**：Q10。过去 30 天的执行中，多少由自动化完成？
- **决定**：项目 owner 决定是否继续投入自动化，以及先自动化哪些模块。
- **定义和公式**：过去 30 天内有结论的 `test_run_cases` 行，按 `executed_via` 分为手工和自动化，计算条数和占比。
- **数据来源**：`test_run_cases.executed_via`、`test_run_cases.executed_at`、`test_run_cases.result`。
- **可行性**：在 `projectStats.executionTrend` 中增加一组按 `executed_via` 的计数。
- **推荐图形**：一条条形码式进度条，分为手工和自动化两段，右侧显示自动化的百分比。
- **图形理由**：这是一个整体中两部分的占比，按规则 1 使用条形码式进度条。只有两个类别，圆环图对两个类别的信息量太少。
- **为什么比替代指标好**：「有自动化脚本的用例数」需要用例和脚本的关联字段，现有数据没有这个字段。执行占比只使用现有字段。

### 6.1 方格矩阵评估

维护者要求：保留方格矩阵需要理由，否则改用图表组件。本报告的结论是删除方格矩阵，改用 M8 的列表。原因如下：

1. 读者的问题是「哪些模块有缺口」。答案是没有方格或没有绿色方格的行，读者必须在大量方格中寻找它们。
2. 方格数量由模块的用例条数决定，大模块占据大部分面积。缺口模块的用例少，所以面积最小。
3. 用例超过 200 条时，一个方格表示多条用例，比例随项目变化。读者不能在两个项目之间比较方格。
4. 方格矩阵需要一个大卡片和「显示全部」按钮。同样的信息用一个只显示缺口的列表就能表示。
5. 用图表组件代替方格矩阵也没有价值：`ScatterChart` 可以画方格，但上面 4 个问题仍然存在。

## 7. 数据有效性

维护者否决 #26 的原因是没有统计有效数据。下面列出读代码时发现的数据问题和本报告的处理方法。

| 问题 | 证据 | 处理方法 |
|---|---|---|
| `test_cases.updated_at` 不表示内容的修改时间 | 该列定义了 `$onUpdate(() => new Date())`。Drizzle 在每个 `update` 语句中自动写入这个值。`openCaseSlot`、`closeCaseSlot`、`reorderTestCasesInTx` 和 `moveTestCaseInTx` 只修改 `sort_order` 或 `module_id`，但也改变 `updated_at`。在模块中插入一条用例时，它后面的所有用例的 `updated_at` 都会改变。 | 不使用 `updated_at`。内容修改时间使用 `case_versions.created_at`：`writeCaseMutation` 只在内容改变时写入新版本。建议维护者另开工单处理这个字段，本报告不修改代码。 |
| 移动用例不写入新版本 | `moveTestCaseInTx` 不调用 `insertCaseVersion`。 | 本报告的指标不依赖版本快照中的 `moduleId`。 |
| 被删除的用例没有记录 | `removeTestCaseInTx` 直接删除行。被测试任务引用的用例不能删除。 | M2 的历史区间只统计没有删除的用例，在页面上不需要说明，因为影响小。 |
| 导入和手工新建无法区分 | `createNewCase`（导入）调用 `createTestCaseInTx`，版本说明都是「创建用例」。`source_ref` 不为空可以表示外部来源，但 MCP 和手工新建也可以填写这个字段。 | 见开放问题 5。 |
| `completed_at` 可以变为空 | 测试任务从已完成回到测试中时，`buildStatusPatch` 把 `completed_at` 设为空。 | M7 只统计状态是已完成或已提交的测试任务。 |
| `executed_at` 只保存最后一次执行 | 修改执行结果时 `executed_at` 被覆盖；改回未测时它被设为空。 | M4、M5、M6 都按每条 `test_run_cases` 的最终执行结果统计。 |
| 被删除的测试任务的执行结果没有记录 | `test_run_cases.run_id` 级联删除。 | M4、M5、M6 只统计现存的测试任务。 |

## 8. 不推荐的指标

### 8.1 考虑过但不放进概览

| 指标 | 原因 |
|---|---|
| 项目通过率（全部时间） | 一条用例在多个测试任务中执行时被计算多次。重新测试会提高通过率。读者看到这个数后没有明确的决定。M5 用最新执行结果代替它。 |
| 每周通过率折线 | 执行很少的区间也会显示 100% 或 0%，读者会误解。M6 同时显示工作量和执行结果。 |
| 用例总数趋势（累积） | 它只增不减，主要表示过去的累积，看不出最近是否停滞。M2 的新增趋势回答同样的问题。按 `case_versions` 快照重建每个区间的用例状态，查询的开销也大。 |
| 每人新增用例数、每人执行数排行 | 这些数容易被刷高，例如拆分用例或快速标记结果。它们评价个人，不支持项目层面的决定。 |
| 每条用例的步骤数或「用例质量分」 | 容易被刷高，并且步骤多不表示质量高。 |
| 用例类型分布（`case_type`） | 读者看到后没有对应的决定。 |
| 标签分布（`tags`） | 标签是自由文本，没有统一的含义。 |
| 测试任务状态分布（待评审、待测试等各多少个） | M3 已经逐个显示进行中的测试任务和它们的状态，一个总分布不能告诉读者处理哪一个。 |
| 每个测试任务的通过率、按模块和优先级的执行结果 | 这些属于测试任务报告（#39），不在本工单范围内。 |

### 8.2 需要新数据，不进入第一版

| 指标 | 缺少的数据 |
|---|---|
| 未关闭的缺陷数 | `test_run_cases.defect_status` 是 Jira 同步的自由文本，没有统一的「已关闭」定义。关联缺陷是可选操作，计数会偏少。需要统一的缺陷状态字段。 |
| 需求覆盖率 | 平台没有需求实体。 |
| 测试任务按期完成率 | `test_runs` 没有计划完成日期字段。 |
| 平均执行时长、工时 | `test_run_cases` 只保存一个执行时间，没有开始时间和时长。 |
| 有自动化脚本的用例占比 | 用例和自动化脚本之间没有关联字段。M10 用执行占比代替。 |
| 不稳定用例（自动化结果反复变化） | `test_run_case_events` 有执行结果的历史，但还没有区分纠正错误和真正的重复执行。需要先定义规则，第一版不做。 |

## 10. 开放问题（需要维护者决定）

1. **条形码式进度条和环形进度图的边界**：本报告的规则是，列表中的行或多个实例并排时用条形码式进度条，整个项目只出现一次的比率用环形进度图。请确认这条规则。
2. **用例状态的图形**：维护者的第二条评论把用例状态列为圆环图的例子，但 #19 和 #26 使用条形码式进度条。本报告采用圆环图。请确认。
3. **测试任务报告的执行结果**：#19 和 #39 规定执行结果用条形码式进度条，第二条评论把执行结果列为圆环图的例子。本报告只对概览的 M5 采用圆环图，不修改 #39。请确认 #39 是否也要改变。
4. **时间窗口**：本报告使用从现在向前的 7 天区间，不使用自然周。如果周报需要自然周，需要确定一周从哪天开始，以及使用哪个时区。
5. **导入的用例是否计入新增**：现有数据不能可靠地区分导入和手工新建。可选方案：（a）全部计入，在 Tooltip 中说明；（b）用 `source_ref` 不为空近似判断导入，接受误差；（c）以后增加字段。本报告推荐（a）。
6. **阈值**：执行覆盖率的时间窗口为 30 天，P0/P1 列表为 90 天，草稿停留为 14 天，测试任务停滞为 7 天。这些值是否需要放进项目设置？本报告推荐第一版使用固定值。
7. **阻塞是否算已执行**：本报告不把阻塞算作已执行，因为阻塞表示用例没有真正执行。请确认。
8. **P3 指标**：M9 和 M10 是否放进第一版。
